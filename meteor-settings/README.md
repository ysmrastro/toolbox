# 流星撮影セッティング

機材構成・流星群・撮影目的を選ぶと、理論に基づいた露出時間・F値・ISO と、その設定で
写せる暗さ（到達等級）・火球を白飛びさせない限界・1コマに収まる確率を算出する Web アプリ。

- URL: https://ysmrastro.github.io/toolbox/meteor-settings/
- フレームワーク不使用の静的ファイルのみ。GitHub Pages で動作。
- PWA 対応（ホーム画面に追加してオフラインでも動く）。

> **オフライン動作は要件ではなく「あわよくば動けばよい」程度**（ユーザーの言葉で
> 「圏外でも動くぐらいの仕様にしない程度」）。「スマホアプリっぽくしたい」という要望に
> 対して PWA を選んだ結果として付いてきた実装上の選択で、ユーザーが立てた方針ではない。
>
> - 動かなくなっていたら直すが、それは仕様違反ではない
> - **これを守るために機能を制限しない**（「オフラインで動かないから却下」はしない）
> - 通信を使う機能は「取れたときだけ表示する」作りにすればよい
- スマホ・タブレット・PC に対応。画面幅で3つのレイアウトを切り替える。

## レイアウト

| 画面幅 | レイアウト |
|---|---|
| 〜699px（スマホ） | 1カラム480px＋下部タブ。上部に推奨値のサマリーを常時表示 |
| 700〜1099px（タブレット縦） | 1カラム680px＋下部タブ。固定バーは全幅に伸ばし中身のみ中央寄せ |
| 1100〜1499px（タブレット横・PC） | 2カラム。左に機材と条件（各カラム内は2段組）、右に結果を追従表示。タブとサマリーは非表示 |
| 1500px〜（大画面PC） | 3カラム（機材 / 条件 / 結果） |

1100px 以上ではタブ切り替えが不要になり、入力を変えると右の結果が即座に更新される。
「計算の前提と出典」と「設定」は狭い画面ではボトムシート、広い画面では中央のダイアログ（Escapeで閉じる）。
設定はボトムナビの4つ目から開く。ボトムナビを隠す 1100px 以上ではアプリバーの ⚙ から開く
（`.appbar__action--wide`）。

## 表示テーマ

ボトムナビの「設定」から 端末に合わせる / ダーク / ライト / アストロ を選ぶ。
選択値は `localStorage` の **`ms-theme`**（入力内容とは別キー）に入れ、
`index.html` 冒頭のインライン script が最初の描画より前に読んで
`<html data-theme>` を立てる。これを JS の後から当てるとダークが一瞬見えてちらつく。

- 実効テーマは `data-theme="dark|light|astro"`、ユーザーの選択は `data-theme-pref`（`auto` を含む）
- `auto` のときだけ `prefers-color-scheme` の変化に追従する
- 色は `style.css` 冒頭の `:root[data-theme=...]` で `--tb-*` / `--ms-*` を差し替える。
  **個別の指定に生の色を書かない**（テーマを足したときに1箇所だけ取り残される）
- `color-scheme` もテーマに合わせる。日付ピッカーや数値スピナーが夜間に白く光るのを防ぐ
- アストロの絵文字は `--ms-icon-filter` で赤単色に寄せる。
  **先に暗くしてから彩度を上げること**（明るい色は赤にならず橙〜黄に転ぶ）。
  `sepia` 後の色相は約35°なので `hue-rotate(-35deg)` が赤で、行き過ぎるとピンクになる
- PWA のステータスバー色（`meta[name=theme-color]`）も切り替え時に書き換える

### 撮影計画タイムライン

`astro.js` の `nightTimeline()` が夜ごとの時刻をまとめて返す。

- その夜の範囲は「現地 12:00 から翌 12:00」。深夜1時を指定しても同じ夜として扱う
- 日没・市民薄明・天文薄明・月出没は `findCrossing()` で高度が閾値をまたぐ時刻を線形内挿して求める（5分刻みで走査）
- **狙い目**＝天文薄明のあいだ かつ 月が地平線下 かつ 放射点が地平線上、の3条件がそろう区間
- 放射点高度は10分刻みの系列にして SVG の折れ線で描く。`viewBox` を引き伸ばすので
  線幅は `vector-effect: non-scaling-stroke` にする
- 15群 × 夜の計算はそれなりに重いので、`app.js` 側で「夜・地点・群」をキーに結果を持ち回す
  （`timelineFor()` / `calendarRows()`）。`renderCond` の暗夜表示もこの結果を使い回している

### 年間カレンダー

各群の極大の夜を `nightTimeline()` で評価し、`狙える時間`（狙い目の合計）と
放射点の最高高度から4段階（当たり年／まあまあ／条件わるい／見込みなし）に分ける。
評価式は `min(狙える時間/5h, 1) × min(最高高度/50°, 1)` の素朴なもので、
**出現数の絶対値ではなく条件の良し悪しの目安**。

### 画角プレビュー

カメラの向きを中心にした**心射投影**（gnomonic projection）で、レンズが写す範囲を
そのまま長方形に描く。canvas に手描きで、外部ライブラリは使わない。

- 星は `stars.js`（**Yale 輝星星表 BSC5 から 5.0等までの1,630星・36KB**）。
  生成は `tools/build-stars.py`（開発用）で、**結果をリポジトリに入れて実行時は取得しない**
- 生成スクリプトは既知の等級（シリウス −1.46 等）と照合してから書き出す。
  合わなければ失敗して止まる（ポラリスは変光星なので星表の 2.02 等を正とする）
- **星座線は入れていない**。星座の結び方は星表に含まれず、よく使われるデータには
  再配布条件が付くものが多いため。向きの手がかりは1等星クラスの固有名で取る
- 放射点から45°の円は、球面三角で放射点まわりに96点を打って投影している
- canvas は表示されていないと幅が0で描けないので、タブが表示された時点
  （`endTrack()`）と画面幅の変化で描き直す（`redrawFov()`）

### 機材セット

`GEAR_KEYS` に挙げた項目（カメラ・センサー・レンズ・ピント・インターバル・赤道儀）だけを
名前付きで `localStorage` に保存する。日時・場所・空の暗さは**現場の条件**なので含めない。
機材を手で変えると保存内容と食い違うので、選択は自動で外れる（`detachGearSet()`）。

### 画面を消さない（Screen Wake Lock）

- 取得はユーザー操作か表示中でないと端末に断られるので、**失敗しても黙って諦める**
- バックグラウンドに回ると解除されるため、`visibilitychange` で取り直す
- 非対応の端末ではスイッチを無効にして、その旨を出す

### 設定の共有（URL）

`#s=<base64url(JSON)>` に入力内容を載せる。

- **クエリ（`?s=`）に載せる**。ハッシュ（`#s=`）はメッセージアプリや短縮URLの経路で
  落ちることがあるため。読み取りは `?s=` と `#s=` の両方を受ける（古いリンクも開ける）
- **初期値と同じ項目は載せない**。さらにセンサーの値がカメラのプリセットどおりなら
  カメラIDだけにするので、既定に近い設定なら URL は 200 文字ほどで収まる
- 受信側は **カメラIDのプリセットを当ててから URL の値で上書きする**。
  この順でないと、手で変えたセンサー値がプリセットに戻ってしまう
- 取り込んだらハッシュを外す（次に開いたときは自分の設定に戻る）
- 受け付けるのは state に元からあるキーで、数値・真偽・文字列・null のものだけ

### 結果カードの画像

外部ライブラリを使わず canvas に手で描く（1200×630）。色は
`getComputedStyle` で画面のテーマから読むので、見えているとおりの配色で出る。

**共有では画像と「同じ設定で開けるURL」を一緒に渡す。** X に投稿すると画像が本文に付き、
リンクから相手が同じ設定で開ける。共有先によって `url` フィールドが落ちることがあるので、
URLは本文（`text`）に入れて渡す。端末の対応状況に応じて3段階に落とす。

1. 画像＋本文（URL入り）で共有 — `canShare({files, text})`
2. 画像だけ共有し、URLはクリップボードにコピー — `canShare({files})`
3. ファイルを共有できない端末は本文（URL入り）だけ共有

**リンクだけを投稿したときのカード画像は設定を反映しない**（共通の `ogp.png` が出る）。
設定ごとの画像を出すにはサーバー側で生成する必要があり、静的サイトでは実現できない。
画像を添付して投稿すれば、そちらが本文に表示されるのでこの制約は問題にならない。

## 文字サイズ

設定シートから 小（本文16px）/ 中（18px）/ 大（20px）を選ぶ。
ルート（`html`）の `font-size` を差し替える方式で、文字だけでなく固定バーの高さや
タップ目標も一緒に伸びる。**そのために CSS の寸法はすべて rem で書いてある**
（px で固定すると文字だけ大きくなってバーからはみ出す）。
選択値は `localStorage` の `ms-text-size`、テーマと同じくインライン script が
最初の描画より前に当てる。

ホーム画面から起動（standalone）すると端末の文字サイズ設定が効かないため、
アプリ側に持たせる必要がある。ピンチズームは無効化していない。

### タイポグラフィの基準（eu-phoria デザイン基準 v1）

- 文字サイズは **rem** 指定で、px 換算が**偶数の梯子**（12/14/16/18/20/24/28/32/36px）に乗ること
- **主要ユーザー層向けの下限は 12px**（`--ms-fs-label`）。
  10px（`--ms-fs-stamp`）は**読了目的でない要素のみ** = アプリバーのバージョン表記だけ
- 共通CSS（`shared/css/variables.css`）の `sm`（13.6px）と `lg`（18.4px）は奇数pxなので、
  `style.css` の `:root` で 14px / 18px に上書きしている（他ツールには影響しない）
- v1.4.0 で、それまで 9〜11.5px だったラベル類（サマリー・タブ・目盛り・バッジ・
  カード見出し）をすべて 12px 以上に引き上げた
- フォントは基準では Noto Sans JP だが、**和文 Web フォントは 1MB 前後になる**ため
  導入せず、Apple 系の標準和文フォント（Hiragino Kaku Gothic ProN）優先のままにしている
  （意図的な逸脱）

## バージョン

アプリバー右上とⓘシートの末尾に、バージョンと更新日を小さく表示している。

| 変更の種類 | 上げ方 |
|---|---|
| バグ修正 | パッチを +0.0.1 |
| 機能追加 | マイナーを +0.1（パッチは 0 に戻す） |
| メジャー | よほどの変更のときだけ |

更新日時は `YYYY-MM-DD HH:MM`。アプリバーでは3段（バージョン／日付／時刻）で表示する。

リリースは**必ずスクリプトで打つ**。手で書くと必ずどこかを忘れるか、時刻を推測で書く。

```bash
python3 meteor-settings/tools/release.py 1.6.0   # 4か所＋更新時刻をまとめて打つ
node meteor-settings/selftest.js                 # そろっているか検査
```

打たれるのは次の4か所。

1. `data.js` の `MS_DATA.appVersion`
2. `data.js` の `MS_DATA.appUpdated`（**スクリプトが実行時の時刻を入れる**）
3. `index.html` の `<meta name="app-version">` と、js/css の `?v=`（全部）
4. `sw.js` の `VERSION`

`selftest.js` が「4か所の一致」と「**更新時刻が未来でないこと**」を検査して落ちる。

> **なぜスクリプトにしたか**: `appUpdated` を手打ちしていて、実際のコミット時刻より
> 最大2時間先の値を入れていた（v1.3.1〜1.5.0）。ユーザーが未来時刻に気づいて発覚した。
> 時刻は推測で書けてしまうので、書ける余地をなくすしかない。

### 更新履歴

`data.js` の `MS_DATA.changelog`（新しいものを上）。リリースのたびに1件足す。
ⓘシートの冒頭のリンクから飛べる。**書くのは使う人に見える変化だけ**で、
内部の整理やドキュメント修正は載せない。

## 画面が真っ白になった事故（v1.3.2 で対策）

**症状**: iPhone と Android の両方で、開いても本文がまったく表示されない。
アプリバーとサマリー（「—」表示）とボトムナビだけが出る。

**原因**: `index.html` と JS の**版が食い違ったまま起動していた**。
`index.html` はキャッシュ優先で返していたため、Service Worker のキャッシュ更新の
途中では「古い `index.html` ＋ 新しい `app.js`」の組み合わせになり得る
（`fetch` ハンドラがファイルごとに独立して背景更新するため、キャッシュの中で版が混ざる）。
新しい JS が古い HTML に無い要素を触って例外になり、`init()` が途中で止まって
どの `.page` にも `.active` が付かないまま終わる → 本文が空。

実際に v1.2.0 の `index.html` ＋ v1.3.1 の JS を並べて再現した:

| | 旧構造（v1.3.1） | 新構造（v1.3.2） |
|---|---|---|
| 表示 | **本文が完全に空・お知らせもなし** | 機材ページが出る |
| 復帰 | ユーザーには手段なし | 帯で「作り直す」を出す＋1回は自動で直す |

**対策（4段構え）**

1. **HTML はネットワーク優先**（`sw.js`）。オフラインのときだけキャッシュを使う。
   古い HTML が新しい JS と組み合わされる元を断つ
2. **js/css の URL に `?v=バージョン`**。ある `index.html` は自分と同じ版の JS しか読まない
3. **`clients.claim()` をやめた**。開いているページを更新途中で新しい Service Worker に
   乗り換えさせない（乗り換えると、そのページの HTML と後続の JS の版が食い違う）
4. **食い違いを検出して自力で直す**
   - `app.js`: `<meta name="app-version">` と `appVersion` を突き合わせ、違えば
     キャッシュと Service Worker を捨てて**1回だけ**読み直す（`sessionStorage` の
     `ms-recovery` で無限ループを防ぐ）。それでも直らなければ帯で手段を出す
   - `app.js`: 起動処理全体を `try`/`catch` で包み、落ちても最低1ページは表示する
   - `index.html`: **末尾のインライン script**が保険。`app.js` 自体が読めなかった場合は
     `app.js` 側の復帰処理も動けないので、2.5秒後に `.page.active` が無ければ
     HTML 側でキャッシュを捨てて読み直す

1〜3 が再発を防ぎ、4 が「それでも起きたとき」に真っ白を避ける。
**古い版の JS には 4 が無いので、この対策が効くのは 1.3.2 以降の版に一度到達してから**。

## タッチ操作（`app.js` の `setupGestures()`）

縦のジェスチャーと横のジェスチャーを1つのハンドラで扱い、最初の 12px
（`AXIS_LOCK`）で縦か横かを決めて以後は取り違えないようにしている。
シート表示中と、指の動きが値の操作になる部品（`input[type=range]` / `select` /
`textarea`）の上では何もしない。

### 引っぱって更新（pull-to-refresh）

ブラウザ標準の pull-to-refresh は、PWA を standalone で起動すると存在しない（iOS）か
抑制されるため自前実装している。CSS の `overscroll-behavior-y` は
`contain`（`none` ではない）にして、ブラウザ標準の動きと二重にならないようにしている。

- 画面上端（触り始めた時点で `scrollY <= 0`）で下に引っぱるとインジケーターが出る
- 70px 以上引っぱって離すと更新。それ未満なら元に戻る
- 更新時は Service Worker の `update()` を先に走らせ、待機中の版があれば
  `SKIP_WAITING` を送って取り込んでから `location.reload()` する
- **開いていたタブは維持される**（`state.activePage` を保存し、`init()` で `activateTab()` に渡す）
- タッチのないPCでは使えないため、ⓘシート末尾と設定シートに「更新を確認」ボタンを置いている

### 左右スワイプでタブ移動（トラック方式）

狭い画面では3ページを横並びの `.track` に入れ、トラックごと `translateX` する。
指の動きにそのまま追従し、離した時点でスナップする。タブのタップも同じ道を通る。

- **しきい値**: 画面幅の 28%（`SWIPE_RATIO`）を超えて動かすと移る。
  速く払った場合は `FLICK_SPEED`（0.45px/ms）以上で移動量が小さくても移る
- 端では移動量に 0.3 を掛けて抵抗をつける（引っぱり過ぎない）
- スナップは 300ms の `cubic-bezier(0.22, 0.61, 0.36, 1)`
- 設定はページではなくシートなので、巡回対象の `PAGES` に入れていない
- ボトムナビを隠す 1100px 以上では `.track { display: contents }` にして無効化

#### 注意している2点（触るときはここを壊さないこと）

1. **畳んでいるときとの基準位置の違い**
   表示中でないページは `display: none` で畳む。`height: 0 + overflow: hidden` だと
   中身が文書の高さに算入されたままになり、機材タブでも結果タブの長さ（約4300px）まで
   スクロールできてしまう。畳んでいるあいだトラックに並ぶのは表示中のページだけなので、
   **定位置は `translateX(0)`**。動かすときだけ `.is-animating` で3ページを並べ、
   **定位置が `translateX(-i*100%)`** に変わる（`beginTrack()` / `endTrack()`）。

2. **ページごとの縦スクロール位置**
   3ページが同時に文書内に存在するため縦スクロール位置が共有される。そのままだと
   下までスクロールした状態で横に払うと隣も同じだけスクロールされた状態で入ってくるので、
   ページごとの位置を `scrollMemo` に覚えておき、動かしているあいだだけ隣のページを
   `translateY(離脱時の位置との差)` でずらす。動かし終わりに `translateY` を外して
   実際の `scrollTo` に置き換える（見た目は変わらない）。
   結果としてタブを移ってもそのページの位置に戻る。

## 保存されるもの

すべて端末のブラウザ内（`localStorage`）に置き、サーバーには何も送らない。

## カメラを向ける方向の扱い

方位と高度を入力すると、次の3つを計算する。

### 放射点からの離角（誤差なし）

カメラの向きと放射点の角距離。純粋な幾何計算。

**式③の「高度角」は放射点ではなくカメラを向ける高度である。** 流星は高度約100kmで光るため、
視線距離が `100/sin(高度)` になり、角速度は `ω = v·sin(離角)·sin(カメラ高度)/100` となる。
記事の ω=18°/s は「離角60°・カメラ高度38°」の幾何に相当し
（`asin(18 / ((59/100)·57.3·sin60°)) = 37.94°`）、これを補正の原点にしている。
そのため基準geometryでは補正量がゼロになり、記事の数値がそのまま再現される。

### 空の明るさ（近似値）

自然光（高度約90kmの大気光）と人工光（高度約2kmでの散乱）を別成分として扱い、
それぞれの経路長を van Rhijn 関数で求め、大気減光（0.20等/airmass）をかけて合成する。

```
LPI = 10^(0.4(22.0 - 天頂の空の明るさ)) - 1
空の明るさ(高度) = 22.0 - 2.5·log10(f_自然(高度) + LPI·f_人工(高度))
f(高度) = vanRhijn(高度, 層の高さ) × 10^(-0.4·k·(airmass-1))
```

| カメラの高度 | 大気の厚み | 空の明るさ（暗夜21.6等） | 空の明るさ（郊外18.9等） | 流星の減光 |
|---|---|---|---|---|
| 90° | 1.00 | ±0.00 | ±0.00 | 0.00等 |
| 60° | 1.15 | −0.12 | −0.13 | 0.03等 |
| 45° | 1.41 | −0.28 | −0.29 | 0.08等 |
| 38°（基準） | 1.62 | −0.39 | −0.40 | 0.12等 |
| 30° | 1.99 | −0.52 | −0.55 | 0.20等 |
| 20° | 2.90 | −0.72 | −0.78 | 0.38等 |
| 10° | 5.59 | −0.76 | −0.96 | 0.92等 |

低い方を向くと空が明るくなるうえ流星自身も減光するため**二重に損をする**。
高度10°で増光が飽和して戻るのは、経路が伸びる効果より大気減光が勝つためで、実際の夜空でも起きる挙動。

### 流星自身の減光（近似値）

大気減光係数 0.20等/airmass（晴れた低地の目安）。到達等級と火球の白飛び限界の双方に効く
（減光ぶんだけ火球は「より明るくないと飽和しない」＝白飛びの余裕が増える）。

### 方位による差は含めていない

光害地図は天頂輝度なので、「街の方向を向いたときに空がどれだけ明るいか」は地点の値からは求められない。
周囲の光源分布から Walker則（寄与 ∝ 距離^−2.5）で推定する試作を検証したところ、
小石原川ダム（久留米＝南西・福岡市＝西北西を正しく検出）と輝北天球館（鹿児島市＝西〜北西）では
当たったが、野辺山では諏訪・松本の方向を最暗と誤判定した。地形の遮蔽を無視するためで、
数値として足し込むのは避けた。**同じ高度なら方位によらず同じ空の明るさになる。**

## 赤道儀で追尾する場合

「赤道儀」をオンにすると、日周運動で星が伸びる制約（NPF則）が露出の上限から外れる。
代わりに追尾精度やバッテリーなどの実務的な上限をユーザーが指定する（既定30秒）。

**重要**: 流星は移動天体なので、露出を延ばしても流星の信号は増えず背景だけ増える。
到達等級は露出2倍ごとに 0.38等 悪化するため、追尾しても「長ければ良い」わけではない。
長い露出が有利なのは、コマの切れ目で火球が途切れる確率が下がる点だけである。

基準構成（α7R V + SIGMA 20mm F1.4・小石原川ダム）での比較:

| 目的 | 固定撮影 | 赤道儀（上限30秒） |
|---|---|---|
| 火球狙い | 8秒 / 到達+1.88等 / 収まる67% | **30秒** / 到達+1.21等 / 収まる**90%** |
| バランス | 8秒 / 到達+1.89等 / 収まる67% | 13秒 / 到達+1.65等 / 収まる79% |
| 本数狙い | 2.5秒 / 到達+2.39等 / 収まる14% | **2.5秒（変化なし）** |

本数狙いでは固定撮影でも NPF則の上限に達していないため、**追尾しても設定は変わらない**。
効果があるのは火球狙い寄りの設定に限られる。

## 記事から確定できず、こちらで決めた前提

1. **到達等級の絶対値アンカー**
   記事の「20mm F1.4 でペルセウス座平均(+1.63等)に到達するには空 21.0等が必要」を
   アンカーにした。この前提で空 21.5等では +1.88等となり、記事の「+1.90等」とほぼ一致する。

2. **S/N の式**
   記事の式④は `S/N ∝ 有効口径 / (角速度 × トレイル幅 × √(空の明るさ × 露出時間))`。
   読み出しノイズを扱えるよう `√(空の明るさ×露出時間)` を実際の1画素ノイズ
   `σ = √(背景電子数 + 読み出しノイズ²)` に置き換え、単位を合わせて
   `S/N ∝ D × (画素ピッチ/F値) / (角速度 × トレイル幅 × σ)` としている。
   この形で記事の条件補正表がすべて再現される。既定ではこの式を使い、
   「記事の式のみ」に切り替えると読み出しノイズを無視した式⑤そのままで計算する
   （露出8秒前後では差はほぼゼロ、1秒では 0.32等 の差）。

3. **トレイル幅**
   焦点距離を変えても秒角でのトレイル幅は変えない。これにより記事の
   「焦点距離2倍で +0.75等」がそのまま再現される。ピント精度の影響は係数で与える
   （1.00 = 記事の中央 1.73px、1.63 = 記事の周辺 2.82px）。

4. **背景電子数のスケール定数**
   記事の火球白飛び限界 −4.25等 から逆算した。結果として 15.4 e-/画素
   （空21.0等・8秒・F1.4・3.756µm）となり、読み出しノイズ 1.41 e- に対して
   背景ショットノイズ支配（記事の主張と一致）。

5. **推奨ISO**
   「到達等級の損失が許容値未満に収まる最も低いISO」を選ぶ。火球狙い（許容 0.02等）で
   基準構成は ISO 640 となり記事の推奨値と一致する。

6. **推奨露出**
   NPF則（簡易式）を上限に、目的別スコアを実用シャッター速度の中で最大化する。
   火球狙い＝稼働率 × 途切れない確率／本数狙い＝r^到達等級 × 稼働率／バランス＝両者の対数の平均。

## 光害地図の仕組みと確度

配布タイルは 4bit パレット PNG（16色）で、16色が光害ゾーン
`0 / 1a / 1b / 2a / 2b / 3a / 3b / 4a / 4b / 5a / 5b / 6a / 6b / 7a / 7b / 8` に対応する。
著者の定義（ゾーン+1で人工光3倍、a→bで√3倍、3b/4a境界で人工光=自然光、自然光=22.0等）から

```
LPI（人工光/自然光）= 3^((zone番号-7)/2)   … 帯の下端。zone 4a を index 7 とする
空の明るさ = 22.0 - 2.5·log10(1 + LPI)     … 代表値は帯の対数中央
```

で等級に換算している。

**実装上の注意**: PNG のパレット並び順は**タイルごとに異なる**（エンコーダがタイル単位で
最適化するため）。したがってパレットの index をそのまま使ってはならず、
**RGB値を参照パレット16色と照合して**ゾーンを決めている（`lightpollution.js` の `nearestIndex`）。
一部の外洋タイルは 4bit グレースケール（colortype=0）で、階調は 0 と 34 のみ
＝参照パレットの `#000000`（zone 0）と `#222222`（zone 1a）に一致する。
著者のビューアが欠損タイルを最暗色で描くのと同様に、存在しないタイルは zone 0 として扱う。

### 階調の粗さ

16段階は人工光の対数等分なので、**暗い空ほど細かくなる**。

| 空の領域 | 1段の幅 |
|---|---|
| 21.9〜22.0等 | 0.03〜0.05等 |
| 21.2〜21.7等（好条件の山） | 0.18〜0.26等 |
| 都市部（17〜19等） | 0.55〜0.59等 |

アプリの感度は「空1等 → 到達等級0.5等」なので、狙う暗い空の領域では
到達等級への影響は 0.1等 未満。

## データの確度

- **画素ピッチ**: メーカー公表スペック（センサー実寸 ÷ 有効画素数）から算出。正確。
- **飽和電子数**: α7R V のみ記事の実測値。他機種は α7R V の実測値（2540 e-/µm²）を
  外挿した**推定値**。誤差1段で火球の白飛び限界が ±0.75等 ずれるが、
  **到達等級・推奨露出・推奨ISOには影響しない**。UI 上で「推定」バッジを表示し、手入力もできる。
- **読み出しノイズ**: α7R V の ISO640 実測値 1.41 e- に合わせたモデル
  `σ_r = √((A·100/ISO)² + F²)`。他機種の係数は推定。
- **流星群**: 放射点・対地速度・ZHR・光度分布指数 r は IMO の Working List 相当。
  平均光度は記事のペルセウス座 +1.63等 を基準に一定量オフセットして揃えた便宜的な値。
- **遭遇本数**: 絶対本数は較正できないため、基準構成を 100 とした相対指数のみ表示。
- **天文計算**: 低精度アルゴリズム（太陽 ±0.01°、月 ±0.3°）。設定判断には十分。
  日時は端末のタイムゾーンで解釈する。
